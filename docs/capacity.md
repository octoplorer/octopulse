# 完整服务容量验证

本文保留 2026-10-02 首版实施阶段的历史结果，并追加 2026-10-04 后端架构优化后的本地竞态复测。这些数值描述各次测试的实现和运行条件，不是生产性能保证。当前验收基线与验证范围见 [验收映射](acceptance.md)。

`internal/server/capacity_test.go` 是可复现的真实时间验收测试。通过 `OCTOPULSE_RUN_CAPACITY=1` 启用，默认测试不会执行这个长测。它使用实际 HTTP Server、API 鉴权和 CSRF、探测 Runner、调度器、统计服务、SQLite/PostgreSQL 持久化以及 Shoutrrr 通知 Worker，没有替换探测函数或推进模拟时钟。

每次测试通过管理 API 创建 100 个 HTTP 监控，间隔均为 30 秒，重试次数为 2，重试延迟为 1 秒，请求超时为 5 秒，连续故障与恢复阈值均为 1。目标是真实本地 HTTP 服务，每次请求增加 20ms 响应延迟：

- 70 个服务持续返回成功，每个监控完成 3 轮、3 次请求。
- 20 个服务每轮前两次返回 503，第三次成功，每个监控完成 3 轮、9 次请求。
- 10 个服务前两轮所有请求返回 503，第三轮第一次请求恢复，每个监控完成 3 轮、7 次请求。

测试持续至少 65 秒，断言恰好 300 个完成轮次、460 个持久化尝试及对应的真实 HTTP 请求，没有同一监控的探测或状态区间重叠。故障服务通过真实本地通用 webhook 收到 10 条故障与 10 条恢复通知；20 个 outbox 任务均为 `sent`，各发送一次，测试结束没有待投递任务。崩溃、租约及通知顺序竞争另外由通知模块的双数据库测试覆盖，本测试不声称外部通知拥有 exactly-once 语义。

公共状态页发布全部 100 个监控，启用可用性和延迟展示。4 个匿名客户端和 2 个已登录管理员客户端分别查询公共页与监控列表，每个客户端每 500ms 尝试发出一次请求，上一请求完成后再处理下一 tick，不累积无界请求。测试检查每个成功响应包含 100 个监控、查询没有错误、两类请求各至少完成 20 次以获取延迟分布。p95 如实记录；规格没有定义 API 延迟 SLA，测试不将竞态检测运行中的延迟当作生产性能门槛。

统计服务保持默认每分钟执行聚合和保留清理。准备的历史包含每个监控一条近期成功轮次与关闭的 Up 区间，已有聚合进度，以及一条 15 天旧轮次与一条 4 天旧轮次/尝试。测试断言近期轮次被实际聚合、15 天旧轮次删除、4 天旧尝试删除而其轮次保留。历史样本用于验证探测/查询并发下的聚合和清理，不等同于填充 100 个监控完整 14 天原始数据量。

## 运行方式

```sh
OCTOPULSE_RUN_CAPACITY=1 mise exec -- go test ./internal/server \
  -run '^TestServiceCapacity100Monitors$' -count=1 -v -timeout=120s

OCTOPULSE_RUN_CAPACITY=1 OCTOPULSE_TEST_DB_DRIVER=postgres \
  OCTOPULSE_TEST_POSTGRES_DSN='postgres://USER@HOST:PORT/octopulse_capacity_test?sslmode=disable' \
  mise exec -- go test ./internal/server \
  -run '^TestServiceCapacity100Monitors$' -count=1 -v -timeout=120s
```

再次运行时添加 `-race` 验证实际并发访问。PostgreSQL 必须使用专用测试数据库，测试会创建并清理独立 schema；实例锁覆盖整个数据库，所以不要和其他持有同一数据库实例锁的测试同时运行。SQLite 使用临时数据库，保留正常 WAL、FULL、只读池等生产配置；PostgreSQL 使用正常 pgx 池、事务与实例锁。

## 2026-10-04 架构优化复测

在批量读模型、固定探测 worker 和公开页批量统计接入后，依次运行 SQLite 与 PostgreSQL 18.6 的同一容量测试，均启用 `-race`。测试条件仍为上述 100 个监控、30 秒间隔、6 个查询客户端；两种数据库容量测试没有相互并行。

| 数据库 / 构建 | 持续时间 | 公共查询数 / p95 | 后台查询数 / p95 | 采样 goroutine 峰值 | Go Heap / Sys 峰值 | 通知队列峰值 |
| --- | --- | --- | --- | --- | --- | --- |
| SQLite，`-race` | 65.536s | 516 / 462.68ms | 258 / 210.18ms | 156 | 16.78 / 54.77 MiB | 10 |
| PostgreSQL，`-race` | 65.203s | 516 / 324.96ms | 258 / 234.54ms | 158 | 14.77 / 50.77 MiB | 10 |

两库均完成 300 轮、460 次尝试、20 条真实通知，同项重叠为 0，聚合近期历史 100 轮，旧轮次及尝试清理通过。SQLite 最大计划迟到 1107ms、最长轮次 2097ms；PostgreSQL 分别为 1403ms、2134ms。该测试不包含新运维历史清理 Runner，其保留规则、分批删除和并发更新保护由独立 retention 测试覆盖。

本次没有重跑正常构建容量测试，也没有填充完整 14 天原始数据；历史运行的并发条件不同，表格不用于计算严格的性能提升比例。

## 首版阶段历史结果

验证环境为 Apple M1、16 GiB 内存、macOS Darwin 25.6.0 arm64、Go 1.27.1、PostgreSQL 18.6。本测试记录运行中每 500ms 采样的最大 goroutine 数、Go `HeapAlloc` 和 `Sys`、待投递或发送中任务数，以及请求 p95、轮次最长耗时和相邻计划轮次延迟。Go 内存数值包含同进程测试 HTTP 目标、webhook 和负载客户端，不包含 PostgreSQL、浏览器或系统缓存；它们不是进程 RSS，也不包含竞态检测器的原生影子内存。采样值不代表瞬时绝对峰值。竞态检测会增加 CPU 与内存成本，单独列出。

| 数据库/构建                | 持续时间 | 公共查询数 / p95 | 后台查询数 / p95 | 采样 goroutine 峰值 | Go Heap / Sys 峰值 | 队列峰值 |
| -------------------------- | -------- | ---------------- | ---------------- | ------------------- | ------------------ | -------- |
| SQLite，正常构建           | 65.028s  | 516 / 86.17ms    | 258 / 46.84ms    | 79                  | 28.83 / 54.90 MiB  | 10       |
| PostgreSQL，正常构建       | 65.062s  | 516 / 214.15ms   | 258 / 66.17ms    | 115                 | 32.19 / 55.33 MiB  | 10       |
| SQLite，修复后独立 `-race` | 66.852s  | 73 / 4594.44ms   | 110 / 1642.55ms  | 240                 | 31.07 / 59.02 MiB  | 7        |
| PostgreSQL，修复后 `-race` | 65.274s  | 96 / 4187.36ms   | 157 / 1318.71ms  | 133                 | 23.58 / 54.77 MiB  | 10       |

两个数据库的正常构建及修复后的竞态检测均完成 300 轮、460 次尝试、20 条实际通知，两种保留清理均通过。正常构建及独立 SQLite 竞态检测聚合近期历史 100 轮；PostgreSQL 竞态检测跨越新的闭合聚合桶，聚合 300 轮。SQLite 正常构建最大计划迟到 27ms、单轮最长 2070ms；PostgreSQL 分别为 1036ms、2063ms。修复后的 SQLite 竞态检测分别为 982ms、2128ms，PostgreSQL 竞态检测为 2023ms、2427ms。单轮耗时包含两次 1 秒重试等待；调度器默认每秒扫描一次。

PostgreSQL 的竞态压力运行捕获并修复了一个重复启动轮次的调度竞争：成功提交提升状态代际后，调度扫描取消旧代际的轮次上下文，导致计划完成标记无法清除。修复后以服务生命周期上下文完成收尾，并使用配置版本与 evaluation epoch 区分新计划；确定性交错回归与完整双数据库长测均通过。

竞态检测显著放大纯 Go SQLite 引擎的查询成本。双数据库竞态压测同时运行时曾有两次 SQLite 公共请求触发 10 秒测试客户端超时，该轮未计作通过。表中的最终 SQLite 竞态结果为保持相同 6 客户端、500ms 请求 tick 和 10 秒超时的独立复测，无请求错误；PostgreSQL 竞态结果来自同时运行双压测的一轮。两种运行条件已分别标注，性能数字不作相互等价比较。

当时的测试验证首版实现能够完成指定的 100 监控/30 秒本地工作负载。它不推导跨机器、远端高延迟服务、慢通知提供商或完整长期历史数据量下的吞吐上限。
